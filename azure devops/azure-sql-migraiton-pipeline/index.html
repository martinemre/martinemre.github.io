    Azure SQL Database Migration Between Tenants with Azure DevOps Pipeline

    6 minute read

    What I Needed

    As part of a migration project, I needed to copy numerous Azure SQL databases belonging to different environments from one Azure tenant to another. This copy operation had to be repeated multiple times before the cutover date so that all necessary testing could be completed.

    There were more than 24 databases in total, and trying to handle everything through manual export import processes was becoming unmanageable. With so many variables in play, doing it by hand was not just tedious, it was putting the entire process at risk.

    So I decided to build an automation layer that would make the database copying reliable, repeatable, and sustainable. My first thought was to use Azure Data Factory. But copying via ADF meant selecting tables one by one, and every single run required recreating the schema and permissions from scratch. It quickly became clear that this approach was not going to scale, so I dropped it before sinking too much time into it and pivoted to automating the whole thing through an Azure DevOps pipeline.

    To keep things organized and make it easier to spot problems when they popped up, I broke the copying process down into distinct stages. Inside the pipeline, I designed each step as a separate stage:

    Workflow

    The pipeline was structured around the following stages:

    • 1.Exporting the source database
    • 2.Renaming the existing database on the target Azure SQL server as a backup
    • 3.Temporarily upscaling the target Azure SQL database SKU
    • 4.Importing the source database into the target environment
    • 5.Reducing the maximum database size
    • 6.Disabling the Read Scale feature
    • 7.Downscaling the target Azure SQL database SKU back to its original level

    Stage Details

    The target environment where I needed to perform the database copying had extremely restricted network access. Because of this, external access to Azure SQL databases was simply not possible. This constraint meant I couldn’t use a Microsoft-hosted agent and had to go with a self-hosted agent instead.

    To handle the export and import operations, I set up a self-hosted agent on a Linux VM located inside the target tenant and ran the entire process from that machine.

    1. In the first step, the pipeline connects to the source Azure SQL database and exports it to the /tmp directory on the self-hosted agent. Since /tmp is ephemeral, those files would be gone if the agent ever restarted. For a more reliable and sustainable setup, you might want to store the exported .bacpac file in Azure Blob Storage instead.

    # =========================
# Stage 1 - Export
# =========================
- stage: ExportDatabase
  displayName: Export Source Database
  jobs:
    - job: ExportJob
      displayName: Export SQL DB
      timeoutInMinutes: 180
      steps:
        - task: Bash@3
          displayName: Export SQL DB
          inputs:
            targetType: inline
            script: |
              sqlpackage /Action:Export \
                /SourceServerName:"$(sourceServer)" \
                /SourceDatabaseName:"$(sourceDatabase)" \
                /SourceUser:"$(sourceSqlUser)" \
                /SourcePassword:"$(sourceSqlPassword)" \
                /TargetFile:"/tmp/$(projectName).bacpac"

    2. In the second step, since the database copy operation needed to be repeated multiple times before the cutover date, I decided to rename the existing database in the target environment before each run. This way, the previous version stays intact and can be deleted manually when needed. It also adds a layer of safety by enabling a quick rollback if something goes wrong.

    # =========================
# Stage 2 - Rename Existing Target DB
# =========================
- stage: RenameTargetDatabase
  displayName: Rename Existing Target Database
  dependsOn: ExportDatabase
  condition: succeeded()
  jobs:
    - job: RenameJob
      displayName: Rename Existing Target DB
      steps:
        - task: Bash@3
          displayName: Rename Target Database
          inputs:
            targetType: inline
            script: |
              export PATH="$PATH:/opt/mssql-tools/bin"

              TIMESTAMP=$(date +%Y%m%d_%H%M%S)
              BACKUP_DB_NAME="$(targetDatabase)_backup_${TIMESTAMP}"

              sqlcmd \
                -S "$(targetServer)" \
                -U "$(targetSqlUser)" \
                -P "$(targetSqlPassword)" \
                -d master \
                -Q "ALTER DATABASE [$(targetDatabase)] MODIFY NAME = [${BACKUP_DB_NAME}]"

    3. In the next step, I noticed that importing with the existing SKU was taking well over 90 minutes. So before starting the import, I temporarily bumped the target Azure SQL database up to a Premium SKU. The Premium tier’s higher I/O and DTU capacity made a huge difference, cutting the import time down to roughly 20 minutes.

    # =========================
# Stage 3 - Create New Premium DB
# =========================
- stage: CreatePremiumDatabase
  displayName: Create Premium Target Database
  dependsOn: RenameTargetDatabase
  condition: succeeded()
  jobs:
    - job: CreateDbJob
      displayName: Create Premium SQL DB
      steps:
        - task: AzureCLI@2
          displayName: Create Premium SQL DB
          inputs:
            azureSubscription: 'xx-xx-xx'
            scriptType: bash
            scriptLocation: inlineScript
            inlineScript: |
              az sql db create \
                --resource-group "$(targetResourceGroup)" \
                --server "$(targetServerLogical)" \
                --name "$(targetDatabase)" \
                --service-objective "$(importSku)"

    4. At this point, I imported the database that had been exported on the Linux VM into the target Azure SQL database, which I had already scaled up to Premium in the previous step.

    # =========================
# Stage 4 - Import
# =========================
- stage: ImportDatabase
  displayName: Import Target Database
  dependsOn: CreatePremiumDatabase
  condition: succeeded()
  jobs:
    - job: ImportJob
      displayName: Import SQL DB
      timeoutInMinutes: 240
      steps:
        - task: Bash@3
          displayName: Import SQL DB
          inputs:
            targetType: inline
            script: |
              sqlpackage /Action:Import \
                /TargetServerName:"$(targetServer)" \
                /TargetDatabaseName:"$(targetDatabase)" \
                /TargetUser:"$(targetSqlUser)" \
                /TargetPassword:"$(targetSqlPassword)" \
                /SourceFile:"/tmp/$(projectName).bacpac"

    5. Once the import was done, I had to bring the maximum database size down below 250 GB before I could scale back to the Standard SKU. The target Standard tier simply does not support database sizes above 250 GB, so this was a necessary step.

    # =========================
# Stage 5 - Reduce Max Size
# =========================
- stage: ReduceDatabaseMaxSize
  displayName: Reduce Database Max Size
  dependsOn: ImportDatabase
  condition: succeeded()
  jobs:
    - job: ReduceMaxSizeJob
      displayName: Reduce SQL DB Max Size
      steps:
        - task: AzureCLI@2
          displayName: Reduce Max Size to 200GB
          inputs:
            azureSubscription: 'xx-xx-xx'
            scriptType: bash
            scriptLocation: inlineScript
            inlineScript: |
              az sql db update \
                --resource-group "$(targetResourceGroup)" \
                --server "$(targetServerLogical)" \
                --name "$(targetDatabase)" \
                --max-size 200GB

    6. In this step, to further reduce the database size and make the transition to Standard SKU possible, I disabled the Read Scale feature, which comes enabled by default with the Premium SKU.

    # =========================
# Stage 6 - Disable Read Scale
# =========================
- stage: DisableReadScale
  displayName: Disable Read Scale
  dependsOn: ReduceDatabaseMaxSize
  condition: succeeded()
  jobs:
    - job: DisableReadScaleJob
      displayName: Disable SQL DB Read Scale
      steps:
        - task: AzureCLI@2
          displayName: Disable Read Scale
          inputs:
            azureSubscription: 'xx-xx-xx'
            scriptType: bash
            scriptLocation: inlineScript
            inlineScript: |
              az sql db update \
                --resource-group "$(targetResourceGroup)" \
                --server "$(targetServerLogical)" \
                --name "$(targetDatabase)" \
                --read-scale Disabled

    7. Finally, I scaled the database SKU back down to Standard to align with the target configuration.

    # =========================
# Stage 7 - Scale Down to Standard S1
# =========================
- stage: ScaleDownDatabase
  displayName: Scale Down SQL Database
  dependsOn: DisableReadScale
  condition: succeeded()
  jobs:
    - job: ScaleDownJob
      displayName: Scale Down SQL DB
      steps:
        - task: AzureCLI@2
          displayName: Scale SQL DB to S1
          inputs:
            azureSubscription: 'xx-xx-xx'
            scriptType: bash
            scriptLocation: inlineScript
            inlineScript: |
              az sql db update \
                --resource-group "$(targetResourceGroup)" \
                --server "$(targetServerLogical)" \
                --name "$(targetDatabase)" \
                --service-objective "$(finalSku)"

    Final Notes

    This pipeline is currently meeting our needs and is actively in use. That said, I am already planning the next round of improvements to make the process safer, more observable, and easier to maintain:

    • Adding a Pre-Stage to each pipeline run to verify database availability, connectivity, and permissions before anything else kicks off
    • Replacing the /tmp directory with Azure Blob Storage as a more reliable and persistent solution
    • Moving SQL credentials out of pipeline variables and into Azure Key Vault
    • Introducing a Validation Stage after import to compare table counts and database sizes as a sanity check
    • Building in a Rollback Stage that can be triggered if the export phase fails
    • Setting up proper logging to track import and export durations, sending logs to Log Analytics, and setting up alerts for error conditions
